# EvidenceQA 面试问答

> 按"总体 → 文档处理 → 检索 → RAG → 评测 → 工程化"分组。回答都是基于本项目
> 真实实现，背下来之前先理解，面试官追问时才有底气。

## 总体

**Q1：为什么做这个项目？**

我想证明自己能把"LLM 应用"做成一个完整闭环：不是调一个 API 出个聊天框，
而是覆盖数据接入、处理、检索、生成、评测、部署的工程链路。选企业知识库问答
是因为它的评价标准很客观——回答必须有依据，检索好坏有 Recall@K / MRR 可量化，
这比"写个聊天机器人"更能体现工程能力。

**Q2：整体流程讲一下。**

两条链路。离线链路：上传文档 → 校验 → 清洗 → 按段落切分 → 生成 embedding
存入 SQLite；在线链路：用户提问 → 对问题做 embedding → 与所有 chunk 算余弦
相似度 → 取 Top-K → 拼进 prompt 生成回答 → 返回回答和引用来源。另外有一条
评测链路：用 21 道题跑 Recall@K、MRR、延迟，量化检索质量。

## 文档处理

**Q3：为什么只支持 md/txt？PDF 怎么扩展？**

初版刻意收窄范围，把校验和解析做成可扩展的：`ALLOWED_EXTENSIONS` 决定类型，
统一走"读取文本 → normalize → 切分"管线。加 PDF 只需要新增解析器（如
pdfplumber / PyMuPDF 抽文本），输出仍是一段字符串，后续管线完全不用改。
限制 1 MB 和 UTF-8 校验，是为了避免脏数据进入切分和向量化。

**Q4：切分策略是什么？为什么保留字符范围？**

段落优先：按标题和空行把文档切成语义块，过长的段落再用固定窗口切，相邻窗口
保留重叠上下文，避免把一句话从中间切断。每个 chunk 存 `char_start/char_end`，
这样"这条答案来自原文哪里"可以精确到字符位置，后续做高亮、去重、审计都有依据。

**Q5：正文、chunk、embedding 为什么分开存？**

三层生命周期不同：正文基本不变；chunk 在切分策略调整时会重建；embedding 在
模型升级时全部要重算。分开存可以单独重建某一层（比如只重算向量），也方便做
增量更新。代码里 `replace_document_chunks` 先删旧 chunk 再写新的，embedding
列为空时启动自动回填，就是为这个设计服务的。

## 检索

**Q6：为什么不用现成 Embedding API？特征哈希是什么？只靠它够吗？**

两个原因：面试演示要离线、稳定，不能依赖外网和 Key；特征哈希是确定性的，
同一句话永远得到同一个向量，测试可复现。做法是先把文本 token 化（英文单词 +
中文单字 + 双字元 bigram），每个 token 用哈希映射到 512 维向量，做 L2 归一化。
它本质是词袋模型，能抓住关键词重叠，但不懂语义（"苹果"和"iPhone"不相似），
所以接口层与真实 Embedding 对齐，接 BGE / OpenAI 时只需替换实现类。同时我在
检索层补了 BM25 混合：向量分和关键词分各自 min-max 归一化后按 alpha 融合，
解决"关键词重叠但语义分散"的问题型查询排序靠后的情况——评测集上 MRR 从
0.9683 提升到 1.0，一道原本排第 3 的问题被提到第 1。

**Q7：为什么用余弦相似度？**

向量已经 L2 归一化，余弦相似度等价于点积，值域稳定在 [-1, 1]，好解释、好排序。
归一化还避免长文本天然得分更高的问题——衡量的是"方向"而非"长度"。

**Q8：Top-K 检索是暴力扫描吗？数据量大了怎么办？**

当前是遍历所有 chunk 并行算向量相似度与 BM25 分数，融合排序取 Top-K，demo
规模完全够用。面试官追问就说扩展方案：本地可用 sqlite-vec / FAISS 做 HNSW
近似最近邻，BM25 侧维护倒排索引；上生产用 pgvector 或专用向量库。

## RAG 问答

**Q9：/ask 的完整流程？引用怎么溯源？**

`AskRequest.question` → `search_chunks` 检索 Top-K → 每个片段以
"[文档片段 i，来自《标题》]" 注入 prompt → 生成回答 → 返回 `answer + sources`，
其中 sources 就是命中的 chunk（含文档标题、片段号、字符范围、相似度分数）。
引用与回答是同一批检索结果，用户能逐条回到原文核对。

**Q10：模板回答和 LLM 回答怎么切换？为什么做成 Provider？**

`get_answer_provider()` 支持三种模式：`EVIDENCEQA_ANSWER_PROVIDER=template`
强制离线模板、`llm` 强制 LLM、`auto` 按是否有 `OPENAI_API_KEY` 自动选择
（默认）。两者实现同一个 `AnswerProvider` 协议，`/ask` 不感知具体实现。
好处是：测试和演示强制 `template`，与开发机环境完全隔离、断网可跑；
接新模型只加一个类；LLM 调用失败时 `/ask` 返回 502 并说明原因，而不是
静默出错。

**Q11：怎么防 LLM 幻觉？**

三层：第一，prompt 明确"只根据上下文回答，信息不足就说明"；第二，回答必须
附带引用来源，用户可核查；第三，检索为空时直接返回"未找到相关文档"，不硬编。
诚实讲，prompt 约束只能降低不能消除幻觉，生产上还要加引用忠实度评测和人工抽查。

## 评测

**Q12：Recall@K 和 MRR 怎么算？为什么选这两个？**

每道评测题有"问题 + 目标文档"。Recall@K = 目标文档出现在 Top-K 的比例，
衡量"找不找得到"；MRR 取目标文档第一次出现位置的倒数并求平均，衡量"排得靠不
靠前"。两个指标互补：一个管召回，一个管排序。局限是只评估检索，不评估回答
质量，所以演示时会说明下一步加 LLM-as-judge。

**Q13：延迟怎么测？**

评测时对每次 `search_chunks` 用 `time.perf_counter` 计时，按题目求平均返回
`avg_latency_ms`。注意口径：这是单次检索延迟，不含网络和 LLM 生成时间。

## 工程化

**Q14：错误处理怎么设计？**

上传：类型不对 415、空文件 / 编码错误 422、超 1 MB 413；查不存在的文档 404。
前端控制台把 `detail` 直接展示给用户。测试覆盖这些状态码，保证前后端约定
不会悄悄漂移。

**Q15：测试策略？**

pytest + TestClient，每个测试用临时 SQLite 隔离数据。分层：切分/embedding 单测、
接口测试（上传、检索、问答、评测、错误处理）、UI 测试（静态资源、控制台渲染、
演示库可检索）。conftest 里强制 `EVIDENCEQA_ANSWER_PROVIDER=template`，所以
测试与开发机上的 API Key 无关，任何环境结果一致。共 38 个用例，跑一遍几秒，
CI 在每次 push 自动回归。

**Q16：怎么部署？**

Docker Compose：`docker compose up --build` 一条命令。数据库路径由
`EVIDENCEQA_DB_PATH` 配置，挂命名卷持久化，容器删除不丢数据；加 healthcheck
轮询 `/health`。回答 Provider、模型和 Key 都走环境变量，同一镜像在不同环境
只改配置不改代码。本地开发用 uvicorn `--reload`。

**Q17：如果给你两周，你会怎么改进这个项目？**

优先级：① 接真实 Embedding + 向量索引，重建评测基线；② 回答质量评测
（引用忠实度 + LLM-as-judge）；③ 多租户文档级权限（已做可选 API Key 鉴权）；
④ 重排层和流式回答；⑤ PDF/Word 解析；⑥ 接入更多真实业务文档做压力测试。
改进每一步都用评测集验证，而不是拍脑袋。
