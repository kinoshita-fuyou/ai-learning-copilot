# 研发规范与发布流程

## 分支与代码管理

新功能开发必须从 main 分支创建独立 feature 分支，分支命名格式为 `feature/需求编号-简述`。禁止直接在 main 分支提交代码。代码合入 main 前必须经过至少一位同事的 Code Review，且所有自动化检查通过。紧急修复使用 `hotfix/` 前缀分支，并需要在修复后补充回归测试。

## 测试与质量门槛

所有改动必须附带单元测试，核心模块要求测试覆盖率不低于 80%。提交合入前需要执行完整测试套件，禁止跳过失败用例。接口变更必须同步更新接口文档。涉及支付、权限、数据导出的改动，还需通过安全评审。

## 发布流程

正式发布使用灰度发布：先放量 10% 观察三十分钟，无异常后放量到 50%，再观察三十分钟，全部放量。每次发布必须填写发布单，包含变更内容、回滚方案和负责人。发布窗口为每周二和周四的 21:00 至 23:00，紧急修复可申请绿色通道。

## 故障应急

线上故障按影响范围分为 P0、P1、P2 三级。P0 故障（核心功能不可用）需在 10 分钟内响应，P1 故障需在 30 分钟内响应。故障处理期间每小时通过值班群同步进展。回滚优先于原地修复：P0 故障默认立即回滚到上一个稳定版本，恢复后 24 小时内提交事故报告。

## 数据库变更

所有数据库结构变更必须提交变更评审单，由 DBA 审核通过后方可执行。大表变更需要提供分批执行方案，禁止在业务高峰期执行锁表操作。历史数据迁移需要先在预发环境完整演练，并保留回滚脚本。
